# Minimal usage collector

Owned Cloudflare Worker + dedicated D1 database. The owner approved the dedicated
Free-plan deployment on 2026-10-29. See [deployment verification](DEPLOYMENT.md) for
the exact recipient and checks. No credentials or deployment automation are bundled.
CLI publication/release remains a separate approval.

## Data contract

`POST /v1/count`, `Content-Type: application/json`, at most 256 UTF-8 bytes:

```json
{"version":"0.3.0","category":"drafts"}
```

Only reviewed release versions are accepted (`VERSIONS`); add a version explicitly
when releasing. Categories: `account`, `drafts`, `publishing`, `media`, `tags`,
`analytics`, `comments`, `queue`. Other keys/values and URLs with query strings are
rejected. The application ignores all request headers except content type.

The only database columns are UTC day (generated by the server), release version,
category, and aggregate invocation count. An atomic upsert increments that day's
count; there are no per-invocation rows, identifiers, fingerprints, IP addresses,
user agents, content, tokens, arguments, or errors stored by the application.
Counts measure activity, **not unique people**, and can be inflated by anyone
sending valid requests: this is deliberately an unauthenticated, non-identifying
counter, not trustworthy billing or security data.

On each accepted request the same D1 transaction removes aggregate rows older
than 90 days. If traffic stops, old aggregate rows remain until another accepted
request or an operator deletes them. D1 backups may temporarily retain deleted
aggregate rows. No application request logs, traces, or Logpush are enabled in the
template; do not enable tail consumers or add request logging.

Cloudflare necessarily receives source IP and other transport metadata. This code
cannot promise that Cloudflare's independent infrastructure/security processing
retains none of it. Review the service's current policies and account settings
before enabling collection; do not describe it as fully anonymous.

## Local verification (no HTTP traffic)

```sh
node --test collector/worker.test.mjs
```

Tests use in-memory Requests and a fake D1 binding; they never call a live endpoint.

## Deployment approval checklist

1. Approve the exact owner/account, endpoint and disclosed recipient. Verify the
   account's current Workers/D1 billing plan, quotas and limits; do not assume zero
   cost from the word "free". Do not upgrade a plan or grant new credentials.
2. Approve creation of a dedicated Worker and dedicated D1 database. Do not reuse a
   newsletter/customer database or Worker with request logging enabled.
3. Copy `wrangler.example.jsonc` to a private deployment configuration, add the
   approved D1 binding named `COUNTS`, and apply `schema.sql` to that database.
4. Verify observability logs/traces, invocation logs, Logpush and tail consumers are
   disabled in effective deployed settings, including any account-level exports.
   Review platform retention separately. Enable only the approved HTTPS route.
5. Update the CLI compiled endpoint and its disclosure together after approval.
   Run mocked tests and review the diff. Publishing/releasing remains a separate
   approval; deployment is not permission to release the CLI.
6. Do not perform a real telemetry smoke test without approval for that payload and
   recipient. A health check must not record an event.
